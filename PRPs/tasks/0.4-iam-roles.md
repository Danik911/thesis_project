# Task P0.4 – Create Baseline IAM Roles and Policies

## What to Do
- Define IAM roles for deployment automation (`pharma-test-gen-deploy`), ECS task execution (`pharma-ecs-execution`), and ECS task runtime (`pharma-ecs-task`).
- Attach least-privilege policies granting necessary access to ECR, S3, SQS, Secrets Manager, Bedrock, and CloudWatch.
- Configure trust relationships for GitHub Actions/OIDC or AWS CodePipeline assuming the deploy role.

## Dependencies
- Requires Terraform backend (Task P0.3) to store IAM infrastructure as code.

## Best Practices
- Use IAM policy documents version-controlled in Terraform.
- Enforce condition keys (e.g., `s3:ResourceTag`, `bedrock:ModelId`) to restrict usage.
- Rotate access by using temporary credentials (OIDC) for CI/CD.

## Code Example
```hcl
resource "aws_iam_role" "deploy" {
  name               = "pharma-test-gen-deploy"
  assume_role_policy = data.aws_iam_policy_document.github_oidc.json
}

resource "aws_iam_role_policy" "deploy_permissions" {
  role = aws_iam_role.deploy.id
  policy = jsonencode({
    Version = "2012-10-17",
    Statement = [
      { Effect = "Allow", Action = ["ecs:*", "iam:PassRole", "ecr:*", "s3:*", "sqs:*", "rds:*"], Resource = "*" }
    ]
  })
}
```

## Testing Strategy
- Use IAM Access Analyzer to validate policies have no unintended public access.
- Assume each role (`aws sts assume-role`) and perform smoke tests (e.g., list ECR images, read Secrets Manager) to verify permissions.
- Document ARNs and permissions for future reference in the runbooks.

## Common Issues to Avoid
- Allowing ECS task roles to have wildcard S3 access; scope to required buckets/prefixes.
- Forgetting `iam:PassRole` permission for deployment automation.
- Neglecting to tag roles for compliance tracking and cost allocation.
