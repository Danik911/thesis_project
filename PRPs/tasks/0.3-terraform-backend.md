# Task P0.3 – Establish Terraform Remote State & Backups

## What to Do
- Create the Terraform remote state S3 bucket with versioning and encryption enabled, plus DynamoDB table for state locking.
- Configure Terraform backend (`backend.tf`) pointing to the state bucket and lock table.
- Document state management procedures, including backup/restore and access controls.

## Dependencies
- Requires compliance services (Task P0.2) to ensure logs capture infrastructure changes.

## Best Practices
- Enable bucket versioning and MFA delete for the state bucket to meet Part 11 audit requirements.
- Limit access to the state bucket/DynamoDB table via IAM policies assigned to the deployment role.
- Use consistent naming convention for environment-specific workspaces.

## Code Example
```bash
# Create S3 bucket for Terraform state
aws s3api create-bucket \
  --bucket pharma-test-gen-tfstate-eu \
  --region eu-west-2 \
  --create-bucket-configuration LocationConstraint=eu-west-2

aws s3api put-bucket-versioning \
  --bucket pharma-test-gen-tfstate-eu \
  --versioning-configuration Status=Enabled,MFADelete=Disabled

# Create DynamoDB lock table
aws dynamodb create-table \
  --table-name terraform-locks \
  --attribute-definitions AttributeName=LockID,AttributeType=S \
  --key-schema AttributeName=LockID,KeyType=HASH \
  --billing-mode PAY_PER_REQUEST \
  --region eu-west-2
```

## Testing Strategy
- Run `terraform init` with the configured backend to confirm connectivity.
- Perform a dummy `terraform plan` to create the initial state file.
- Verify state bucket contains versioned objects and DynamoDB table registers locks during concurrent operations.

## Common Issues to Avoid
- Forgetting to enable versioning, jeopardizing rollback capabilities.
- Allowing public access to the state bucket; block all public ACLs and policies.
- Neglecting to document MFA requirements for destructive operations on the state bucket.
