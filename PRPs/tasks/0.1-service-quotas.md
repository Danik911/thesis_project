# Task P0.1 – Validate AWS Service Quotas for Migration

## What to Do
- Inventory the AWS services required for the migration (ECS Fargate, SQS, Aurora Serverless v2, S3, CloudFront, Bedrock, LangFuse stack components) in eu-west-2.
- Verify existing account quotas cover the planned peak load (50 docs/day → up to 10 concurrent jobs) and request increases where necessary.
- Document quota statuses and submit Service Quota increase tickets via AWS Support for any insufficient limits (e.g., Fargate On-Demand vCPU, S3 bucket quotas, Amazon Bedrock TPS).

## Dependencies
- None; prerequisite to infrastructure provisioning (Task 1).

## Best Practices
- Use the AWS Service Quotas dashboard to export quota reports per region.
- Focus on Fargate task counts/vCPU limits, SQS inflight messages (standard queue), Aurora ACU min/max, CloudFront distributions, and Bedrock request quotas.
- Request quota increases at least 5 business days before expected usage spikes.

## Code Example
```bash
# List Fargate quotas
aws service-quotas list-service-quotas \
  --service-code ecs \
  --region eu-west-2 \
  --query 'Quotas[?QuotaCode==`L-1216C47A`]'  # Fargate On-Demand vCPU limit

# Request increase (example)
aws service-quotas request-service-quota-increase \
  --service-code ecs \
  --quota-code L-1216C47A \
  --desired-value 64 \
  --region eu-west-2
```

## Testing Strategy
- Capture screenshots or exports from the Service Quotas console confirming approved limits.
- Track support case IDs and expected completion dates.
- Re-run CLI checks to ensure new quota values are applied before proceeding to infrastructure tasks.

## Common Issues to Avoid
- Overlooking Bedrock throughput limits, causing throttling during peak workloads.
- Assuming default vCPU limits suffice; Fargate often defaults to 20 vCPU.
- Forgetting to verify CloudFront distribution limits when creating multiple environments (dev/staging/prod).
