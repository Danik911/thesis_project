# Task P3.2 – Compose Multi-Service Local Stack

## What to Do
- Build `docker-compose.dev.yml` orchestrating FastAPI, worker, Postgres mock, and SQS LocalStack.
- Wire environment variables to mimic AWS services (Aurora Data API -> local Postgres, SQS -> LocalStack).
- Provide developer docs for running migrations and tests against the local stack.

## Dependencies
- Requires Docker improvements from Task P3.1 and backend adapters (Task P1.1/P1.3).

## Best Practices
- Keep `.env.development` separated from production secrets.
- Use healthcheck dependencies in Compose to ensure services start orderly.
- Document parity gaps between local stack and AWS (e.g., Data API vs psycopg2).

## Code Example
```yaml
version: '3.9'
services:
  api:
    build: .
    command: uvicorn main:app --host 0.0.0.0 --port 8080
    env_file: .env.development
    depends_on:
      postgres:
        condition: service_healthy
    ports:
      - "8080:8080"
  worker:
    build: ./worker
    env_file: .env.development
    depends_on:
      localstack:
        condition: service_started
  postgres:
    image: postgres:15-alpine
    environment:
      POSTGRES_PASSWORD: devpass
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
  localstack:
    image: localstack/localstack:2.3
    environment:
      SERVICES: sqs
      DEFAULT_REGION: eu-central-1
    ports:
      - "4566:4566"
```

## Testing Strategy
- Run end-to-end test suite against Compose stack in CI.
- Validate worker picks messages off LocalStack queue and persists job results.
- Measure parity by comparing local vs AWS schema migrations.

## Common Issues to Avoid
- Forgetting to pre-create SQS queues in LocalStack before workers start.
- Using production AWS credentials in local .env files.
- Ignoring performance differences when mapping Data API to Postgres driver.
