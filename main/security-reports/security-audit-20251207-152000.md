### Finding 2: [CRITICAL] Weak Horizontal Authorization Check
- **File:** `C:\Users\anteb\Desktop\Courses\Projects\thesis_project\main\api\app.py`
- **Lines:** 596-597, 650-651, 736-745, 856-865, 1024-1032

- **Pattern:**
  ```python
  # Line 596-597 - GET /jobs/{job_id}/download
  if job.user_id != user.sub:
      raise HTTPException(status_code=403, detail="Not authorized")

  # Line 650-651 - GET /jobs/{job_id}/result
  if job.user_id != user.sub:
      raise HTTPException(status_code=403, detail="Not authorized")

  # Line 736-745 - GET /jobs/{job_id}
  if job.user_id != user.sub:
      logger.warning(
          f"Authorization denied: User {user.sub} ({user.email}) "
          f"attempted to access job {job_id} owned by {job.user_id}"
      )
      raise HTTPException(
          status_code=status.HTTP_403_FORBIDDEN,
          detail=f"CRITICAL: User not authorized to view job {job_id}"
      )
  ```

- **Risk:**
  - **Horizontal Privilege Escalation:** User can access other users' jobs if they can manipulate their JWT `sub` claim
  - **Data Leakage:** URS documents, test results, and approval history exposed to unauthorized users
  - **Regulatory Violation:** GAMP-5 requirement for access controls not properly enforced
  - **Audit Trail Tampering:** Users could access approval records belonging to others

- **Vulnerability Analysis:**
  The authorization check relies solely on comparing `job.user_id` to `user.sub` from the JWT. Issues:
  1. **No cryptographic binding:** The user_id stored in the job record is not cryptographically bound to the user
  2. **Race condition:** Job ownership could change between creation and access
  3. **No role-based checks:** No verification that the user has the required role/permissions
  4. **RBAC not integrated:** The RBAC system exists (`main/src/compliance/rbac_system.py`) but is never called

- **Proof of Concept:**
  ```python
  # Attacker scenario:
  # 1. Create job with user_id = "attacker_user_id"
  # 2. If JWT validation is bypassed (Finding #1), could forge token with different sub
  # 3. Access job created by victim with job_id enumeration

  # Attack flow:
  import requests

  # Attacker enumerates job IDs (UUIDs are predictable if leaked)
  victim_job_id = "fa7a84d2-3c5e-4b1a-9f2d-8e6c7d4a5b3c"

  # If attacker compromises JWT signing (Finding #1 - exposed CLERK_SECRET_KEY)
  # they can forge a token with victim's sub claim
  forged_token = create_forged_jwt(sub="victim_user_id")

  # Access victim's job
  response = requests.get(
      f"https://api.example.com/jobs/{victim_job_id}",
      headers={"Authorization": f"Bearer {forged_token}"}
  )
  # Result: Access granted due to matching user_id
  ```

                 f"attempted to access job {job_id} owned by {job.user_id}"
