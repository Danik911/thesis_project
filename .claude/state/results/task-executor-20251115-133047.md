## Design Decisions

### 1. LocalStack 3.x over 2.3 (Task Specification)
**Decision:** Use `localstack/localstack:3` instead of `2.3` specified in task example
**Rationale:**
- LocalStack 3.x is current stable version (since Nov 2023)
- Better SQS support and bug fixes
- Task example was outdated reference code
- Research findings confirmed 3.x as recommended version

### 2. Health Check Dependencies for Postgres
**Decision:** Use `depends_on` with `condition: service_healthy` for postgres
**Rationale:**
- Prevents "connection refused" errors in API/worker containers
- Ensures database initialization (init.sql) completes before dependent services start
- Matches Docker Compose best practices from official documentation
- Uses `pg_isready` as reliable health indicator (10s interval, 30s grace period, 5 retries)

### 3. Named Volumes for Persistence
**Decision:** Use named volumes (`postgres-data`, `localstack-data`, `output-data`, `chroma-data`) instead of bind mounts
**Rationale:**
- Docker-managed volumes are portable across platforms (WSL2, Linux, macOS)
- Better performance on Windows (Docker Desktop optimization)
- Explicit reset command: `docker-compose down --volumes` (prevents accidental data loss)
- Clearer separation of code (bind mounts) vs data (named volumes)

### 4. Init Scripts via Ready Hook (LocalStack)
**Decision:** Mount init script to `/etc/localstack/init/ready.d/init.sh` instead of `/docker-entrypoint-initdb.d/`
**Rationale:**
- LocalStack 3.x convention: ready.d scripts run AFTER services are fully initialized
- Postgres convention: docker-entrypoint-initdb.d runs BEFORE database is ready (wrong for SQS)
- Prevents race condition where SQS queue creation fails if service not ready
- Matches LocalStack official documentation

### 5. AMD64 Build Target in Development
**Decision:** Use `linux/amd64` platform even on ARM64 host (Qualcomm Oryon)
**Rationale:**
- Production parity with ECS Fargate (Intel-based)
- Validates containers work in target platform before deployment
- ARM64 emulation via QEMU is acceptable for development (slower but functional)
- Optional ARM64 builds possible via `--build-arg BUILDPLATFORM=linux/arm64` for faster local iteration

### 6. Dual-Mode Environment Configuration
**Decision:** Support both ChromaDB and pgvector, both local storage and S3 (via commented config)
**Rationale:**
- Developers can test both storage adapters without changing code
- ChromaDB default (faster, simpler) for typical development
- pgvector mode for Aurora parity testing before migration
- Matches abstraction layer design from Task 1.1, 1.2

### 7. Comprehensive Parity Gap Documentation
**Decision:** Dedicate entire section of LOCAL_DEVELOPMENT.md to parity gaps table and behavioral differences
**Rationale:**
- GAMP-5 validation requirement: understand differences between dev and prod
- Risk assessment: identify which behaviors cannot be tested locally
- Guides migration testing strategy (what to focus on in AWS staging)
- Transparent communication to validation team

### 8. Executable Permissions on Init Scripts
**Decision:** Run `chmod +x scripts/init-localstack.sh` as part of implementation
**Rationale:**
- Git on Windows may not preserve executable bits (WSL2 environment)
- Prevents "permission denied" errors when LocalStack tries to execute script
- Explicit chmod ensures consistency across platforms
- Better developer experience (one less troubleshooting step)

## Known Limitations

### 1. LocalStack SQS Feature Gaps

**Limitation:** LocalStack SQS may not perfectly replicate all AWS SQS features
**Specific Gaps:**
- FIFO queue exactly-once delivery not guaranteed
- Message deduplication based on content hash (AWS: message deduplication ID)
- Approximate message count may differ from AWS implementation

**Impact:** Low (development/testing only)
**Mitigation:** Document in parity gaps section, test FIFO behavior in AWS staging environment

### 2. Aurora Data API vs Postgres Protocol Latency

**Limitation:** Local Postgres uses binary protocol (~1-5ms latency), Aurora Data API uses HTTP/JSON (~50-100ms)
**Impact:** Moderate (performance characteristics differ by 10-50x)
**Mitigation:**
- Document in parity gaps table
- Tune timeout configurations conservatively (use AWS-like values in dev)
- Load test in AWS staging to validate latency assumptions

### 3. No S3 Object Lock Immutability

**Limitation:** Local filesystem storage has no immutability enforcement (S3 Object Lock equivalent)
**Impact:** Moderate (cannot test compliance lock features locally)
**Mitigation:**
- Document in parity gaps section
- Test S3 Object Lock separately in AWS environment (Task 5.2)
- Use synthetic test data (no risk of accidental modification of regulated data)

### 4. Single Container per Service (No Autoscaling)

**Limitation:** Docker Compose runs 1 instance of API and 1 instance of worker (no horizontal scaling)
**Impact:** Low (cannot test autoscaling behavior, load distribution)
**Mitigation:**
- Document in parity gaps section
- Test autoscaling separately in ECS Fargate staging (Task 4.4)
- Use `docker-compose --scale worker=3` for basic multi-instance testing (not recommended due to shared volume issues)

### 5. Init Scripts Run Once Only (Postgres)

**Limitation:** `postgres-init.sql` runs ONCE on first container startup (when volume is empty)
**Impact:** Low (developer workflow issue, not functional limitation)
**Mitigation:**
- Document in LOCAL_DEVELOPMENT.md troubleshooting section
- Provide explicit reset command: `docker-compose down --volumes`
- Schema changes require volume deletion or manual SQL execution

### 6. WSL2 Platform-Specific Considerations

**Limitation:** Development on Windows 11 with WSL2 and ARM64 (Qualcomm Oryon)
**Specific Issues:**
- AMD64 container emulation slower than native ARM64 (~30-50% overhead)
- File permissions on bind mounts may behave differently than Linux
- Docker Desktop for Windows resource limits (RAM, CPU)

**Impact:** Low (performance only, not functionality)
**Mitigation:**
- Document platform notes in CLAUDE.md and LOCAL_DEVELOPMENT.md
- Optional ARM64 builds for faster local development (add `--build-arg BUILDPLATFORM=linux/arm64`)
- Validate AMD64 images before AWS deployment (production target)
