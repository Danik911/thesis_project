## Root Cause Analysis

### Issue Description
After Docker container rebuild, all API calls from the frontend were failing with 401 "JWT expired" errors. The backend was correctly rejecting expired Clerk JWT tokens.

### Root Cause
Clerk JWT tokens have a **60-second default expiration**. When `getToken()` is called:
1. Clerk checks if the cached token is still valid
2. If the token is about to expire, Clerk triggers a **background refresh**
3. However, `getToken()` may return the old (about-to-expire) token immediately
4. The backend then rejects the request with 401

The `useJobStatusPolling.ts` hook already had retry logic (added in Task 3.15, Issue 9), but:
- `generate.tsx` made direct fetch calls without retry
- `[id].tsx` made direct fetch calls without retry

### Why It Occurred
The token refresh is **asynchronous** - Clerk refreshes tokens in the background, but the initial API call with the old token fails. The solution is to retry after a delay, giving Clerk time to complete the refresh.

### Fix Approach
Created a centralized `authenticatedFetch` utility that wraps all API calls with:
1. Automatic token injection from Clerk
2. 401 retry with exponential backoff (2s, 4s, 8s)
3. Max 3 retries before failing
4. Consistent logging for debugging

```typescript
export async function authenticatedFetch(
    url: string,
    getToken: GetTokenFn,
    options: RequestInit = {},
    retryCount: number = 0
): Promise<Response> {
    const token = await getToken();
    if (!token) {
        throw new Error('Authentication token not available. Please sign in again.');
    }

    const response = await fetch(url, {
        ...options,
        headers: {
            ...options.headers,
            'Authorization': `Bearer ${token}`,
        },
    });

    // Handle 401 with exponential backoff retry
    if (response.status === 401 && retryCount < MAX_RETRIES) {
        const delay = Math.pow(2, retryCount + 1) * 1000; // 2s, 4s, 8s
        console.warn(`[API] Token expired (401), retry ${retryCount + 1}/${MAX_RETRIES} in ${delay}ms...`);
        await new Promise(resolve => setTimeout(resolve, delay));
        return authenticatedFetch(url, getToken, options, retryCount + 1);
    }

    return response;
}
```

## Architecture Notes

### Pattern Applied
The same exponential backoff pattern from `useJobStatusPolling.ts` (Task 3.15, Issue 9) was extracted into a reusable utility. This ensures:
- Consistent retry behavior across all API calls
- Single point of maintenance for auth logic
- NO fallback logic - errors are thrown after max retries

### Why Retry Works
1. First request fails with 401 (token expired)
2. Utility waits 2 seconds (Clerk refreshes token in background)
3. Second request calls `getToken()` again (returns fresh token)
4. Request succeeds

### Console Output
Users may still see `[API] Token expired (401), retry 1/3 in 2000ms...` in the console during normal operation. This is expected behavior and not an error - it indicates the retry mechanism is working correctly.
