## 1. LlamaIndex Workflow Patterns for HIL

### 1.1 Event-Based Architecture

LlamaIndex workflows are **event-driven abstractions** that chain event handling steps together:

```python
from llama_index.core.workflow import (
    Workflow, InputRequiredEvent, HumanResponseEvent,
    StartEvent, StopEvent, Context, JsonSerializer
)

class HILWorkflow(Workflow):
    @step
    async def categorize(self, ctx: Context, ev: StartEvent) -> InputRequiredEvent | StopEvent:
        # AI categorization logic
        confidence = 0.75

        if confidence < 0.85:
            # Trigger HIL - require human approval
            return InputRequiredEvent(
                prefix="Please confirm GAMP-5 category: ",
                user_name="reviewer"
            )

        return StopEvent(result={"category": 4, "confidence": confidence})

    @step
    async def approve(self, ctx: Context, ev: HumanResponseEvent) -> StopEvent:
        # Process human approval
        human_category = int(ev.response)
        return StopEvent(result={"category": human_category, "approved_by": "human"})
```

**Pattern Details:**
- `InputRequiredEvent` pauses workflow and waits for user input
- `HumanResponseEvent` resumes workflow with human decision
- Context (`ctx`) maintains state across steps
- Events flow through async queue system

### 1.2 State Serialization for Persistence

LlamaIndex provides context serialization for saving/restoring workflow state:

```python
from llama_index.core.workflow import JsonSerializer

# Save state after HIL trigger
handler = workflow.run(ctx=ctx)
async for event in handler.stream_events():
    if isinstance(event, InputRequiredEvent):
        # Save context to database
        ctx_dict = handler.ctx.to_dict(serializer=JsonSerializer())
        await db.save_workflow_state(job_id, ctx_dict)
        break  # Pause here

# Restore state later when approval received
ctx_restored = Context.from_dict(
    workflow,
    ctx_dict,
    serializer=JsonSerializer()
)
handler = workflow.run(ctx=ctx_restored)
handler.ctx.send_event(HumanResponseEvent(response=human_category))
```

**Serialization Options:**
- `JsonSerializer`: Simple JSON serialization (fast, limited object types)
- `JsonPickleSerializer`: Pickle-based fallback (slower, supports complex objects)

**Critical Warning:** Use JSON serializer only for serializable types (primitives, dicts, lists). Complex objects like file handlers, connection pools, or database connections will fail.

### 1.3 Checkpointing Pattern

For long-running workflows, use `WorkflowCheckpointer`:

```python
from llama_index.core.workflow import WorkflowCheckpointer

checkpointer = WorkflowCheckpointer()
checkpointer.workflow = my_workflow

# Run workflow with checkpointing
handler = checkpointer.run()
await handler

# Resume from specific checkpoint
ckpt = checkpointer.checkpoints[run_id][step_index]
handler = checkpointer.run_from(checkpoint=ckpt)
result = await handler
```

**Benefits:**
- Automatic step-level checkpoints
- Resume from any completed step
- Fault tolerance for long-running processes

## 2. Known LlamaIndex Issues & Limitations

### 2.1 Cross-Session Resumption Problem (CRITICAL)

**Issue:** When resuming workflows across sessions, workflows reset to initial state instead of continuing from saved checkpoint.

**Observed Behavior:**
```python
# Save context
handler = workflow.run()
ctx_dict = handler.ctx.to_dict(serializer=JsonSerializer())
await db.save(ctx_dict)

# Later: Restore and resume
ctx_restored = Context.from_dict(workflow, ctx_dict, serializer=JsonSerializer())
handler = workflow.run(ctx=ctx_restored)
handler.ctx.send_event(HumanResponseEvent(response=approval))

# PROBLEM: Stream produces initial InputRequiredEvent instead of resuming
async for event in handler.stream_events():
    # Still gets InputRequiredEvent, not continuing from approval step
```

**Root Cause:** Context restoration creates new event streams that restart from `StartEvent` rather than continuing from saved state.

**Workaround:**
- Use `WorkflowCheckpointer.run_from()` instead of manual context restoration
- Store checkpoint objects directly instead of serialized context
- Implement manual state management outside workflow (database-backed)

**Reference:** [GitHub Issue #18019](https://github.com/run-llama/llama_index/issues/18019)

### 2.2 Serialization Issues with Complex Objects

**Issue:** Workflow contexts containing non-serializable objects fail during `to_dict()`:

```python
class MyWorkflow(Workflow):
    @step
    async def start(self, ctx: Context, ev: StartEvent):
        # These cause serialization failures:
        ctx.store.put("db_connection", connection)  # ❌ Non-serializable
        ctx.store.put("file_handle", file)          # ❌ Non-serializable
        ctx.store.put("lock", asyncio.Lock())       # ❌ Non-serializable

# Fails with: ValueError: Failed to serialize value: <class 'asyncpg.Connection'>
ctx_dict = ctx.to_dict(serializer=JsonSerializer())
```

**Affected Components:**
- `ChatMemoryBuffer` with custom message storage
- Multi-agent systems with function callbacks (lambdas)
- Database connections, file handles, locks
- LLM client connections

**Solutions:**
1. Store only IDs/references in context, not objects:
```python
ctx.store.put("connection_id", "conn_123")  # ✅ Serializable
db_connection = await get_connection(connection_id)  # Fetch later
```

2. Use custom serializers:
```python
class CustomSerializer(JsonSerializer):
    def serialize(self, obj):
        if isinstance(obj, Connection):
            return {"_type": "connection", "id": obj.id}
        return super().serialize(obj)

    def deserialize(self, data):
        if isinstance(data, dict) and data.get("_type") == "connection":
            return Connection(id=data["id"])  # Reconnect
        return super().deserialize(data)
```

**References:**
- [GitHub Issue #18475 - ChatMemoryBuffer Serialization](https://github.com/run-llama/llama_index/issues/18475)
- [GitHub Issue #18069 - Multi-agent Serialization](https://github.com/run-llama/llama_index/issues/18069)

### 2.3 InputRequiredEvent Streaming Issues

**Issue:** When pausing workflow with `InputRequiredEvent`, resuming via `stream_events()` may not properly nest child events.

**Best Practice:**
```python
# ✅ CORRECT: Break from stream and resume separately
handler = workflow.run()
async for event in handler.stream_events():
    if isinstance(event, InputRequiredEvent):
        break  # Pause here

# Get human input, send response
response = input(event.prefix)
handler.ctx.send_event(HumanResponseEvent(response=response))

# ✅ Resume in NEW stream
async for event in handler.stream_events():
    # Continue processing
```

## 3. FastAPI + PostgreSQL Job State Management

### 3.1 Async Connection Pooling with asyncpg

**Pattern:** Use `asyncpg.create_pool()` for efficient connection reuse:

```python
import asyncpg

# Create pool (recommended for server applications)
pool = await asyncpg.create_pool(
    "postgresql://user:pass@localhost/testdb",
    min_size=2,      # Keep 2 connections warm
    max_size=10,     # Max 10 concurrent connections
    command_timeout=60
)

# Use from endpoints
async def get_job(job_id: str) -> JobRecord:
    async with pool.acquire() as conn:
        row = await conn.fetchrow(
            "SELECT * FROM jobs WHERE job_id = $1",
            job_id
        )
        return JobRecord(**row) if row else None

# In lifespan:
@asynccontextmanager
async def lifespan(app: FastAPI):
    pool = await asyncpg.create_pool(DATABASE_URL)
    # ... startup ...
    yield
    # Shutdown
    await pool.close()
```

**Performance Comparison:**
- **No pooling:** Create new connection for each query → 1.568 seconds
- **With pooling:** Reuse connections from pool → 0.234 seconds (6.7× faster)

**Critical Rules:**
1. Always use `async with pool.acquire()` to ensure connection return
2. Never leak connections - check for `PoolEmptyError`
3. Set `max_size` based on concurrent request load

**References:**
- [asyncpg Documentation](https://magicstack.github.io/asyncpg/current/usage.html)
- [Stack Overflow: asyncpg pooling](https://stackoverflow.com/questions/42242093/asyncpg-connection-vs-connection-pool)

### 3.2 Database Polling for Job Approval Workflows

**Pattern:** Worker polls database for approval status instead of in-memory state:

```python
async def _wait_for_hil_approval(
    job_id: str,
    db_job_repo: PostgresJobRepository,
    timeout_seconds: int = 3600,
    poll_interval_seconds: int = 2
) -> bool:
    """Poll PostgreSQL for approval status."""

    timeout_at = datetime.now(UTC) + timedelta(seconds=timeout_seconds)

    while datetime.now(UTC) < timeout_at:
        await asyncio.sleep(poll_interval_seconds)

        # Query database for latest status
        job = await db_job_repo.get(job_id)

        if job.status == JobStatus.APPROVED:
            return True
        elif job.status == JobStatus.REJECTED:
            return False

    # Timeout - auto-reject
    return False
```

**Advantages:**
- ✅ Works across container restarts (state in database)
- ✅ Scales to multiple workers (shared database state)
- ✅ Audit trail by database transactions
- ✅ No in-memory state loss

**Disadvantages:**
- ❌ Higher latency (polling interval delays approval)
- ❌ Database load (frequent queries)

**Optimization Tips:**
1. Use database notifications (LISTEN/NOTIFY) instead of polling for low-latency:
```python
async def _wait_for_hil_approval_notify(job_id: str, db_pool):
    """Use PostgreSQL LISTEN/NOTIFY for instant updates."""

    async with db_pool.acquire() as conn:
        await conn.add_listener(f"job_{job_id}_approval")
        try:
            while True:
                msg = await asyncio.wait_for(conn.get_messages(), timeout=3600)
                if msg:
                    return msg["payload"] == "APPROVED"
        finally:
            await conn.remove_listener(f"job_{job_id}_approval")
```

2. Reduce polling interval during active approval windows
3. Implement exponential backoff: start fast, slow down over time

### 3.3 Job State Transitions and Atomicity

**Critical Pattern:** Ensure atomic state updates:

```python
# Job states for HIL workflow
class JobStatus(str, Enum):
    PENDING = "pending"              # Initial
    PROCESSING = "processing"        # Worker started
    AWAITING_APPROVAL = "awaiting_approval"  # HIL triggered
    APPROVED = "approved"            # Human approved
    REJECTED = "rejected"            # Human rejected
    COMPLETED = "completed"          # Done
    FAILED = "failed"                # Permanent failure

# State transitions
async def set_approval_status(
    job_id: str,
    status: JobStatus,
    human_category: int | None = None
) -> None:
    """Atomic update of approval status."""
    async with pool.acquire() as conn:
        # Single UPDATE transaction ensures atomicity
        await conn.execute(
            """
            UPDATE jobs SET
                status = $2,
                human_category = $3,
                updated_at = NOW()
            WHERE job_id = $1
            """,
            job_id, status.value, human_category
        )
```

**GAMP-5 Requirement:** Every state transition must be logged to audit trail with timestamp, user ID, and justification.

## 4. Langfuse Tracing for HIL Workflows

### 4.1 Why @observe Decorator Fails

**Issue:** The `@observe` decorator serializes ALL function parameters, including non-serializable objects:

```python
from langfuse.decorators import observe

@observe  # ❌ PROBLEM: Tries to serialize 'file' and 'pool'
async def submit_job(
    file: UploadFile,  # Non-serializable file descriptor
    pool: asyncpg.Pool  # Non-serializable connection pool
):
    pass

# Error: Langfuse tries to JSON-serialize parameters
# UploadFile has open file descriptor → infinite hang
# asyncpg.Pool has network connections → serialization error
```

**Why It Hangs:**
1. `@observe` wraps function to capture input/output
2. During wrapping, it tries to serialize `file` parameter
3. `UploadFile` contains `SpooledTemporaryFile` object
4. JSON serialization recursively tries to serialize file handle
5. File descriptor serialization never completes → hang

### 4.2 Manual Span Pattern (Recommended)

**Solution:** Create spans manually with only serializable metadata:

```python
from langfuse import Langfuse

langfuse = Langfuse()

async def submit_job(
    file: UploadFile,
    pool: asyncpg.Pool,
    user_id: str
) -> JobSubmitResponse:
    """Submit job without @observe decorator."""

    # Create span with ONLY serializable metadata
    span = langfuse.start_span(
        name="submit_job",
        input={
            "filename": file.filename,
            "content_type": file.content_type,
            # ❌ DON'T include: file object, pool, non-serializable items
        },
        metadata={
            "user_id": user_id,  # ✅ Serializable
            "endpoint": "POST /jobs"
        }
    )

    try:
        # Process job
        urs_content = await file.read()
        urs_hash = hashlib.sha256(urs_content).hexdigest()

        # Save to storage
        storage_key = await storage.save_artifact(...)

        # Update span
        span.update(output={
            "job_id": job_id,
            "status": "submitted",
            "storage_key": storage_key
        })

        return JobSubmitResponse(job_id=job_id)

    except Exception as e:
        span.update(output={"error": str(e)}, level="ERROR")
        raise
    finally:
        span.end()
        langfuse.flush()  # Ensure trace sent
```

**Key Points:**
- Create span AFTER getting unsafe objects (not in decorator)
- Only serialize filename, user_id, status - not the objects
- Always call `span.end()` and `langfuse.flush()`
- Manual spans give full control over what's traced

### 4.3 Nesting Spans for Distributed Tracing

**Pattern:** Nest spans properly to avoid multiple root traces:

```python
# ❌ WRONG: Multiple unrelated spans create separate traces
span1 = langfuse.start_span(name="step1", input={...})
span1.end()

span2 = langfuse.start_span(name="step2", input={...})  # NEW TRACE!
span2.end()

# ✅ CORRECT: Nest spans under parent
async def process_job(job_id: str):
    parent_span = langfuse.start_span(name="process_job")

    try:
        # Child spans automatically nest
        child1 = parent_span.start_child_span(name="categorize")
        # ... do work ...
        child1.end()

        child2 = parent_span.start_child_span(name="generate_tests")
        # ... do work ...
        child2.end()

    finally:
        parent_span.end()
        langfuse.flush()
```

**Distributed Tracing with Trace IDs:**

```python
import uuid

# Create deterministic trace ID from job_id
trace_id = f"job_{job_id}".replace("-", "")[:32].lower()

span = langfuse.start_span(
    name="hil_approval",
    trace_id=trace_id,  # Links all related spans
    metadata={"job_id": job_id}
)
```

**References:**
- [Langfuse Trace IDs Documentation](https://langfuse.com/docs/observability/features/trace-ids-and-distributed-tracing)
- [Langfuse Python SDK Decorators](https://langfuse.com/docs/sdk/python/decorators)

## 5. Implementation Gotchas & Solutions

### 5.1 404 "Job Not Found" After Approval (CRITICAL)

**Symptom:**
- User submits job → created with ID
- Worker processes, triggers HIL
- User approves via `POST /jobs/{job_id}/approval` → **404 Not Found**

**Root Causes & Solutions:**

| Cause | Check | Fix |
|-------|-------|-----|
| Job not persisted to database | Database logs, job query | Ensure `await db_job_repo.create(job)` succeeds in `POST /jobs` |
| Database connection pool exhausted | `PoolEmptyError` in logs | Increase `max_size` parameter in `asyncpg.create_pool()` |
| Job ID mismatch (UUID vs string) | Trace job_id types | Ensure consistent UUID/string conversion |
| Database transaction isolation | Check transaction levels | Use explicit `async with conn.transaction():` |
| In-memory repo used instead of DB | Check `db_job_repo is None` | Set `DATABASE_URL` environment variable |
| Concurrent access race condition | Check timestamps in audit log | Use database locks: `FOR UPDATE` |

**Debug Checklist:**

                if msg:

await db_pool.execute(

### 5.4 Race Conditions in Approval Workflow

**Risk:** Concurrent requests might race to update job status

**Protection:**
```python
# Use database row-level lock
async def set_approval_status_atomic(
    job_id: str,
    status: JobStatus,
    human_category: int | None = None
) -> None:
    """Atomically update with row lock."""
    async with pool.acquire() as conn:
        async with conn.transaction():
            # Lock row for update
            job = await conn.fetchrow(
                "SELECT * FROM jobs WHERE job_id = $1 FOR UPDATE",
                job_id
            )

            if job.status != JobStatus.AWAITING_APPROVAL:
                raise ValueError("Job not awaiting approval")

            # Now safe to update
            await conn.execute(
                "UPDATE jobs SET status = $2, human_category = $3 WHERE job_id = $1",
                job_id, status.value, human_category
            )
```

**Solution:** Log all state transitions with full context:

async def set_approval_status(

## 6. Pharmaceutical Compliance Requirements

### 6.1 GAMP-5 for HIL Workflows

GAMP-5 (Good Automated Manufacturing Practice) requires:

| Requirement | Implementation | Audit Evidence |
|-------------|-----------------|-----------------|
| **Traceability** | Job ID linked to URS, approval, results | Audit trail with timestamps |
| **Audit Trail** | Log all state changes with user/time | Database audit log table |
| **Validation** | Workflow categorization validated | Test cases + approval records |
| **Change Control** | Track which approval decision was made | Before/after values in audit log |
| **Data Integrity** | Job data immutable after approval | Database constraints, checksums |
| **Backup/Recovery** | State persisted to PostgreSQL | Disaster recovery procedures |
| **Electronic Signature** | User digitally signs approval | Digital signature field with iat/exp |

**Reference:** [GAMP-5: Computerized System Validation in Pharma](https://intuitionlabs.ai/articles/gamp-5-guidelines-system-validation)

### 6.2 ALCOA+ Principles for HIL State

HIL decisions must maintain ALCOA+ compliance:

- **Attributable:** Who made the decision (user_id, email, timestamp)
- **Legible:** Human-readable in audit trail
- **Contemporaneous:** Logged immediately when approved
- **Original:** First record of decision (no modifications)
- **Accurate:** Verified by human reviewer
- **Complete:** All required fields populated
- **Consistent:** Standard format across all approvals
- **Enduring:** Permanent storage in PostgreSQL
- **Available:** Accessible for audit retrieval

### 6.3 21 CFR Part 11 for Electronic Records

For future AWS production, must meet FDA 21 CFR Part 11:

- Electronic records must have computer system controls
- Cannot rely on person memory or external records
- Must have data integrity controls (signatures, timestamps)
- Records protected from unauthorized access/modification
- System documentation required (validation reports)

# FastAPI endpoint for job approval
@app.post("/jobs/{job_id}/approval", response_model=ApprovalResponse)
async def submit_job_approval(
    job_id: str,
    approval_request: ApprovalRequest,
    db_job_repo: DbJobRepositoryDep,
    pool: asyncpg.Pool,
    user: CurrentUserDep,
) -> ApprovalResponse:
    """Submit human approval with full GAMP-5 compliance."""

    async with pool.acquire() as conn:
        async with conn.transaction():
            # Atomically get and lock job
            job = await conn.fetchrow(
                "SELECT * FROM jobs WHERE job_id = $1 FOR UPDATE",
                job_id
            )

            if not job:
                raise HTTPException(status_code=404, detail="Job not found")

            if job['status'] != 'awaiting_approval':
                raise HTTPException(status_code=400,
                    detail=f"Job not awaiting approval (status: {job['status']})")

            # Validate timeout not expired
            if datetime.now(UTC) > job['approval_timeout_at']:
                # Auto-reject on timeout
                await conn.execute(
                    "UPDATE jobs SET status = $2 WHERE job_id = $1",
                    job_id, 'rejected'
                )
                raise HTTPException(status_code=408,
                    detail="Approval timeout expired")

            # Determine new status
            if approval_request.approval_decision == ApprovalDecision.APPROVE:
                new_status = 'approved'
            elif approval_request.approval_decision == ApprovalDecision.REJECT:
                new_status = 'rejected'
            else:  # REQUEST_REVISION
                new_status = 'awaiting_approval'

            # Update job status atomically
            await conn.execute(
                """
                UPDATE jobs SET
                    status = $2,
                    human_category = $3,
                    updated_at = NOW()
                WHERE job_id = $1
                """,
                job_id,
                new_status,
                approval_request.human_category
            )

            # Log to audit trail for GAMP-5 compliance
            await conn.execute(
                """
                INSERT INTO audit_log
                    (job_id, event_type, user_id, user_email,
                     status, human_category, justification, metadata, timestamp)
                VALUES ($1, $2, $3, $4, $5, $6, $7, $8, NOW())
                """,
                job_id,
                'approval_decision',
                user.sub,  # Clerk user ID
                user.email,  # ALCOA+ attribution
                new_status,
                approval_request.human_category,
                approval_request.justification,
                json.dumps({
                    'ai_category': job['gamp_category'],
                    'ai_confidence': job.get('confidence'),
                    'digital_signature': f"{user.sub}_{datetime.now(UTC).isoformat()}"
                })
            )

    # Notify workers (if using LISTEN/NOTIFY)
    await pool.execute(
        f"NOTIFY job_approval_{job_id}, $1",
        json.dumps({
            "status": new_status,
            "human_category": approval_request.human_category
        })
    )

    # Log trace
    if langfuse:
        span = langfuse.start_span(
            name="approval_decision",
            trace_id=f"job_{job_id}",
            input={
                "job_id": job_id,
                "decision": approval_request.approval_decision.value
            },
            metadata={"user_id": user.sub}
        )
        span.update(output={"new_status": new_status})
        span.end()
        langfuse.flush()

    return ApprovalResponse(
        job_id=job_id,
        status=new_status,
        message=f"Approval recorded: {new_status}"
    )

## 10. Summary: Key Takeaways

### Critical Patterns
1. **Use database polling** for job approval state (not in-memory)
2. **Manual Langfuse spans** to avoid serialization hangs on file/connection objects
3. **Atomic database updates** with explicit transactions to prevent race conditions
4. **Proper span nesting** to avoid multiple traces in Langfuse
5. **Full audit trail** for GAMP-5 compliance on every state transition

### Known Gotchas
1. LlamaIndex workflows reset to initial state when resuming across sessions
2. @observe decorator fails on non-serializable parameters
3. Multiple traces indicate improper span nesting or missing flush()
4. Connection pool exhaustion causes 404-like errors
5. HIL state lost on container restart if not using database

### Compliance Must-Haves
1. Atomic state transitions with database locks
2. Complete audit trail with user/time/justification
3. Digital signatures for approval records
4. Data integrity via checksums and immutability
5. Backup/recovery procedures tested
