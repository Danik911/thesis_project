## Design Decisions

### 1. Base Image Selection: python:3.12-slim-bookworm

**Rationale:**
- ChromaDB does NOT support Alpine Linux (musl libc incompatibility - GitHub issue #2758)
- Debian slim images balance size (~150MB) with compatibility
- Bookworm is Debian 12 (stable, current LTS)
- Includes apt package manager for runtime dependencies

**Alternatives Rejected:**
- Alpine: ChromaDB incompatible
- Distroless: No apt-get for runtime dependencies
- Full Debian: Too large (~800MB base)

### 2. Package Manager: uv (Not pip/poetry)

**Rationale:**
- Project already uses uv (confirmed in pyproject.toml)
- Binary copy from ghcr.io/astral-sh/uv:0.9.8 (pinned version)
- Faster than pip (~10x for cold installs)
- Lock file ensures reproducibility (uv.lock)

**Configuration:**
- UV_COMPILE_BYTECODE=1: Pre-compile .pyc files (~20% startup speedup)
- UV_LINK_MODE=copy: Required for multi-stage Docker builds
- UV_PYTHON_DOWNLOADS=never: Use system Python from base image

### 3. Tini Installation: apt-get (Not static binary)

**Rationale:**
- Matches system package manager (Debian)
- Version pinned to 0.19.* for reproducibility
- Simpler than downloading static binary
- Installs to /usr/bin/tini (standard location)

**Purpose:**
- Runs as PID 1 in container
- Reaps zombie processes (prevents PID table exhaustion)
- Forwards SIGTERM to application (graceful shutdown)
- ALCOA+ compliance: Ensures in-flight transactions complete

### 4. Non-Root User: appuser UID 1000

**Rationale:**
- GAMP-5 security control requirement
- Predictable UID across environments (ECS IAM role mapping)
- Prevents container escape exploits from gaining root on host
- Audit trail can track by UID

**Implementation:**
- Created with useradd -m -u 1000 appuser
- Files copied with --chown=appuser:appuser
- USER appuser directive before ENTRYPOINT

### 5. Layer Caching Strategy

**Order (most stable to most volatile):**
1. Base image + uv installation (rarely changes)
2. Build dependencies apt-get (rarely changes)
3. pyproject.toml + uv.lock (changes on dependency updates)
4. uv sync (cached unless dependencies change)
5. Application code (changes on every commit)

**Benefits:**
- First build: ~5 minutes
- Code change only: ~30 seconds
- Dependency change: ~2 minutes

### 6. Runtime Dependencies Split

**Builder Stage (NOT in final image):**
- gcc: C compiler for native extensions
- libpq-dev: PostgreSQL development headers (~10MB)

**Runtime Stage (in final image):**
- libpq5: PostgreSQL shared library (~300KB)
- curl: Healthcheck endpoint testing
- tini: Init system
- ca-certificates: HTTPS to AWS APIs

**Benefit:** 90% size reduction (10MB → 300KB for PostgreSQL libs)

### 7. Healthcheck Configuration

**Parameters:**
- --interval=30s: Match ECS default
- --timeout=5s: Fast failure detection
- --start-period=10s: Grace period for uvicorn startup (~5-10s)
- --retries=3: 3 consecutive failures before unhealthy

**Endpoint Design:**
- Shallow check (no database queries)
- Fast response (<100ms)
- Returns 200 OK if application running
- Avoids audit log flooding (no @observe decorator)

## Known Limitations

### 1. Build Time (First Build)
- **Limitation:** First build takes ~5 minutes (download all dependencies)
- **Rationale:** Necessary for reproducibility (no pre-cached layers)
- **Mitigation:** Cache mounts reduce incremental builds to ~30 seconds

### 2. Platform Specificity
- **Limitation:** Dockerfiles target linux/amd64 only
- **Rationale:** AWS ECS Fargate requirement (arm64 support coming in Task 4.1)
- **Impact:** Cannot run natively on Apple Silicon M1/M2 Macs without emulation

### 3. Health Endpoint Simplicity
- **Limitation:** /health endpoint does not check database connectivity
- **Rationale:** Shallow checks prevent healthcheck from causing load
- **Mitigation:** Deep healthcheck can be added later at /health/deep (optional)

### 4. Worker Healthcheck
- **Limitation:** Worker container has NO healthcheck
- **Rationale:** Workers don't expose HTTP endpoints
- **Mitigation:** ECS monitors via task lifecycle events (not HTTP)

### 5. Secrets Management
- **Limitation:** Secrets not baked into images (good security practice)
- **Requirement:** Must pass secrets via ECS task definition (AWS Secrets Manager)
- **Documentation:** Covered in DOCKER_BUILD_GUIDE.md ECS section

### 6. Trivy Not Installed Locally
- **Limitation:** Security scanning requires Trivy installation
- **Mitigation:** Script provides installation instructions

### 7. Windows Build Script Compatibility
