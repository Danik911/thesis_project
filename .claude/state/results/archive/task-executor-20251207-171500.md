## Implementation Summary

Implemented a global daily job limit feature for cost control during staging/development. The feature:

1. Counts jobs created today (UTC) in PostgreSQL, excluding 'failed' jobs
2. Blocks new job submissions when limit is reached (HTTP 429)
3. Provides a quota endpoint for frontend to display remaining jobs
4. Configurable via DAILY_JOB_LIMIT environment variable (default: 10)

---

## Design Decisions

### 1. Status Exclusion Logic
- **Decision:** Exclude only 'failed' jobs from count
- **Rationale:** Failed jobs represent system errors (not user cost). Rejected jobs (human decision) still consumed LLM resources and should count toward limit.

### 2. In-Memory Mode Handling
- **Decision:** Skip limit check when db_job_repo is None
- **Rationale:** In-memory mode is for local development only. No persistent storage means limit would reset on every restart, making enforcement meaningless.

### 3. Default Limit Value
- **Decision:** Default to 10 jobs/day
- **Rationale:** Reasonable for staging environment. Low enough to prevent cost overruns, high enough for development testing.

### 4. Quota Endpoint Authentication
- **Decision:** No authentication required for GET /jobs/quota
- **Rationale:** Allows frontend to display quota status before user attempts submission. Read-only endpoint with no sensitive data.

### 5. Database Connection Pattern
- **Decision:** Use `async with self._pool.acquire() as conn:` pattern
- **Rationale:** Matches existing codebase patterns. Task spec had incorrect pattern (`self.pool.fetchval`).

## Known Limitations

1. **Race Conditions:** Two concurrent submissions at count=9 (limit=10) could both pass check. Acceptable for staging use case per task spec.

2. **Midnight Boundary:** Job submitted at 23:59:59 UTC with count query, created at 00:00:01 UTC. Acceptable edge case.

3. **Negative Limit:** DAILY_JOB_LIMIT=-1 treated as disabled (same as 0). ValueError on non-integer crashes app startup (config error, not runtime).
