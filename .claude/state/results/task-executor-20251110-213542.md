## Design Decisions

1. **PostgreSQL pgvector instead of "S3 Vectors"**
   - Rationale: "S3 Vectors" does not exist as an AWS service. After comprehensive research by context-collector, the intended implementation is PostgreSQL with pgvector extension in Aurora Serverless v2.
   - Benefits: Single database for relational (audit logs, job metadata) and vector data, native audit triggers for ALCOA+ compliance, excellent metadata filtering via B-tree indexes, cost-effective (~$5/month at minimal Aurora capacity).

2. **Protocol-Based Abstraction (VectorStoreProvider)**
   - Rationale: Follows Task 1.1's successful StorageProvider pattern for consistency across codebase.
   - Benefits: Clear contract definition, dependency injection via VectorStoreFactory, seamless backend switching, testable interfaces.

3. **Embedding Model Caching at Provider Level**
   - Rationale: Prevents redundant instantiation and API setup overhead for OpenAI embeddings.
   - Implementation: Cache embedding model instance ONCE at adapter initialization, set in LlamaIndex Settings.embed_model for global reuse.
   - Benefits: Reduced embedding costs (OpenAI charges per token), faster document processing.

4. **Async Methods with Explicit Error Handling**
   - Rationale: Align with LlamaIndex 0.12.0+ async patterns and pharmaceutical NO FALLBACK LOGIC requirements.
   - Implementation: All errors raise RuntimeError with CRITICAL prefix and full diagnostic context (query parameters, mode, stack traces).
   - Benefits: GAMP-5 compliance, explicit failure visibility, comprehensive audit trails.

5. **GAMP-5 Metadata Validation**
   - Rationale: Pharmaceutical compliance mandates validation of all metadata before storage.
   - Implementation: Validate required fields (gamp_category, created_by, document_type) and GAMP category values (1, 3, 4, 5) on every document addition.
   - Benefits: Prevents invalid data from entering vector store, ensures regulatory compliance.

6. **Over-Fetching Strategy for ChromaDB Metadata Filtering**
   - Rationale: ChromaDB performs post-filtering after retrieval, causing severe performance degradation at scale (5+ minutes for 40K docs).
   - Implementation: Over-fetch 2x top_k when metadata filters applied, warn users about performance limitations.
   - Benefits: Compensates for ChromaDB's algorithmic limitations, maintains functionality while warning users.
